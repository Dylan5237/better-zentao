# 01 需求分析

> 目的：把访谈与需求收集中的原始诉求整理清楚，找到背后的根因，对现有的不同做法给出统一建议，最终形成需求清单。本文是 02（用户故事）和 03（协作规范）的依据。

## 1. 分析方法

```text
原始诉求（S1、S4） → 按角色整理痛点 → 归并为根因 → 用第一性原理判断"什么必须成立"
   → 两条手段：① 协作规范（约定怎么用禅道） ② 系统能力（让规范零成本执行）
   → 需求清单（FR / NFR） → 用户故事（02）
```

**第一性原理：** 一条工作要被有效协作，必须始终能回答五个问题。禅道里的每个字段、每条规范、每个系统能力，都是为了让这五个问题有可靠的答案。

| 基本问题 | 必须保留的信息 | 现状能否回答 |
| --- | --- | --- |
| 为什么做 | 原始问题、反馈者、来源 | 部分：口头或企微来的需求常丢失来源 |
| 承诺做什么 | 产品、L3 计划、**本次实现范围**、验收条件 | 部分：设计文档混有旧内容，范围不清 |
| 谁在何时做 | 当前处理人、任务负责人、截止日期 | 部分：`指派给`字段语义混乱 |
| 怎样证明做完 | 评审、传递、开发、测试、验收、交付的完成证据 | 差：阶段任务按顺序事后创建，缺环节难发现 |
| 下一步谁接 | 当前阶段、接续责任 | 差：只能靠人记忆与口头通知 |

## 3. 根因分析

27 个痛点可以归并为 6 个根因。**规范要解决根因，系统要让规范执行起来没有成本。**

| 根因 | 说明 | 导致的痛点 | 解决手段 |
| --- | --- | --- | --- |
| **C1 入口门槛高** | 提需求要懂产品、模块、计划、类别、必填项，业务和研发都不愿意录 | P01、P03、P04、P10、P26 | 系统：一句话提需；规范：先录后做（N15） |
| **C2 `指派给`一个字段承载多种含义** | 同一个字段既表示"下一步谁行动"，又被用来表示"最终谁接收"，草稿阶段就指派给研发，导致研发不知道该做什么、设计找不到要维护的需求 | P07、P08、P09 | 规范：指派即行动（N05）；系统：角色分离、移交、通知 |
| **C3 接续靠记忆** | 测试、验收、交付任务在上一阶段完成后才由人想起来创建；没有通知机制 | P08、P09、P20、P22 | 规范：拆解时一次建齐阶段任务（N07）；系统：缺口规则与通知 |
| **C4 计划语义不统一** | 计划有的按"月 × 模块负责人"，有的按"发布版本"，一条需求只能挂一个计划，两种语义互相挤占 | P15、P21、P23、P24 | 规范：L3 只表达月度模块计划，版本另用标签（N04） |
| **C5 信息散落在多个页面** | 需求、计划、迭代、任务、子任务、Bug 分布在不同视图，汇总与操作要来回跳转 | P02、P05、P17、P18、P21、P23 | 系统：聚合视图（进展卡片、五桶、排期面板、一站式拆解） |
| **C6 记录不完整、不规范** | 范围不写清、Bug 不关联、先做后录、多人任务、历史任务不关；禅道外的工作没有记录 | P10、P11、P12、P13、P16、P19 | 规范：正文模板、Bug 关联、关闭规范；系统：自动补全、校验与巡检 |

## 4. 现有做法差异与统一建议

访谈记录如实保留了各视角的不同做法。**设计的任务是在理解这些差异的基础上，推荐一种对所有角色都有实际帮助的统一用法**，并说明理由与过渡办法。详细规范见 03。

| 议题 | 现有做法 | 分析 | 统一建议 |
| --- | --- | --- | --- |
| 需求与任务的粒度 | A：一条需求一个任务，多人时拆子任务（设计主管、后端）<br>B：设计按调研、概设、原型、评审、传递拆多个任务；研发需求下按研发、测试、验收、交付依次建任务（天宫管理） | A 的价值是操作简单；B 的价值是能看出阶段、能判断完成。两者其实并不矛盾：A 说的是"一个阶段不要拆得太碎"，B 说的是"不同阶段要分开" | **一阶段一任务，一人一子任务**（N06、N07）。由系统按模板一键生成，操作成本与 A 相同，信息量与 B 相同 |
| 测试等下游任务何时创建 | 研发完成后再创建测试任务，测试通过后再创建验收任务 | 串行事后创建是"迟迟没有测试任务"风险（P22）的直接原因；测试人员也无法提前排期 | **拆解时一次建齐所需的阶段任务**，下游任务处于"未开始"状态（N07） |
| 计划的组织方式 | A：按月、按模块，计划名称标注负责人（天宫管理、前端）<br>B：按当月发布版本，一个版本一个计划（后端） | 禅道一条需求只能挂一个计划。B 会让需求离开 L3 计划，破坏"所有需求挂 L3""按 L3 看完成情况"两条管理要求；而 B 想解决的"版本发布前必须完成哪些需求"，可以用版本标签 + 发布日历表达 | **L3 统一为"月 × 模块（负责人）"**；发布版本用需求的版本标签表达，系统提供发布就绪视图（N04、N12） |
| 需求何时指派给研发 | 有的在草稿或评审中就指派给研发主管 | 违背"指派给 = 下一步谁行动"，研发看到却不能动，设计找不到要维护的需求 | **激活前指派给状态维护人（设计人员），激活即移交研发主管**（N05） |
| 设计类与研发类何时拆分 | 管理视角：传递后在计划下创建研发类需求<br>设计视角：判断需要设计时就分别建两条 | 提前建研发类需求有利于月度排期，但处于草稿时容易被误指派；传递后再建又可能漏建 | **需要设计时先建设计类；评审通过后，由移交操作自动生成研发类需求**，并带上范围与关联（N02、N05） |
| 跨模块提需 | 前端模块设计人员直接向后端建模研发人员提需求 | 直接提给研发人员会绕过研发主管的排期，研发主管看不到负载 | **提给被依赖模块的研发主管**，可注明建议人选；发起方设计人员是状态维护人（N10） |
| 任务协作方式 | 多人任务与子任务并存，后端倾向子任务 | 多人任务的责任与逾期难以归属（顺序多人任务只显示当前顺位人） | **不使用多人任务，协作一律用子任务**（N08） |
| Bug 的创建入口 | 主菜单"测试"或执行下的测试入口，关联执行非必填 | 不关联需求，Bug 就无法计入需求进展与发布门禁 | **Bug 必须关联需求；测试中发现的同时关联执行**（N11） |
| 研发需求的完成 | 测试任务完成后需求才算完成；也存在测试未完成就发布 | 发布与完成是两件事；测试未完成就发布应当是有记录的例外 | **发布门禁**：版本内需求测试完成且无未关闭严重 Bug，例外需登记（N12） |
| 月底挪月 | 研发主管月底把做不完的需求挪到下个月 | 挪月本身合理，但不留记录就无法统计顺延，也无法回答"原计划完成了多少" | **通过系统挪月并记录原因，月初保存承诺快照**（N13） |
| 历史任务关闭 | 每两个月回看一次，确认需求完成再关闭任务 | 周期性清理是"关闭需求时没有同步关闭任务"的补救 | **关闭需求时一并关闭其任务**；周期清理作为兜底（N14） |
| 任务开始时间 | 必填，被认为是负担 | 开始时间对排期面板有用，负担来自手工填写 | **保留字段，由系统按规则自动填写**（N07） |
| 先做后录 | 研发先做，再请产品补录 | 根因是提需门槛高（C1） | **先录后做**：一句话建草稿需求，Git 提交带需求号（N15） |

## 5. 手段分工：规范、系统与人工

| 手段 | 负责的事 | 例子 |
| --- | --- | --- |
| 协作规范（03） | 约定对象怎么用、谁在什么时候做什么 | 指派即行动、一阶段一任务、L3 统一语义 |
| 系统能力（07） | 让规范零成本执行；聚合视图；确定性计算；发现偏差 | 一句话提需、一键拆解、移交、排期面板、风险巡检、每日摘要 |
| 人工判断 | 系统只给事实和建议，由人决定 | 是否需要设计、指派给谁、是否挪月、是否豁免发布门禁 |

**原则：** 系统不替人做业务决定，不自动关闭、不自动指派、不追责；系统负责让"按规范做"比"不按规范做"更省事。

## 7. 范围

**第一版（P1–P2）做：** FR-01 至 FR-20 及 Web 门户（FR-23）——即在原定本地 stdio MCP、CLI 与定时摘要之外，**同步建设 Web 门户协作工作台**，与 Agent/CLI 共享同一业务内核、领域规则和权限边界。

**不做：**

- 独立工作流引擎（禅道仍为唯一事实来源，Web 门户复用同一业务服务内核与写入安全模型，不绕过禅道状态机、不另立口径）。
- 修改禅道的表结构或系统配置。
- 批量改写历史数据（历史数据只做兼容识别与提示）。
- 个人工作量排名或绩效评分。
- 自动关闭需求、自动指派、自动追责。
