## 2. 通用约定

### 2.1 输入

- 所有输入用 zod 校验，未知字段拒绝（`strict()`）。
- 人员参数接受账号、中文名或拼音；产品、模块、计划参数接受 ID 或名称。名称解析由服务端完成，解析不唯一时返回 `AMBIGUOUS_ENTITY` 并给出候选，**不得猜**。
- 日期参数用 `YYYY-MM-DD`；月份用 `YYYY-MM`；也接受 `本月`、`下月`、`上月`，由服务端按配置时区解析。
- 列表参数有默认 `limit`（20）与硬上限（100），超出时返回 `truncated=true`。

### 2.2 输出：查询结果

```ts
// src/contracts/result.ts
export interface QueryResult<T> {
  ok: true;
  data: T;
  scope: {                          // 本次查询的口径，Agent 必须原样转述给用户
    asOf: string;                   // 数据时间 ISO8601
    filters: Record<string, unknown>;
    timeBasis?: string;             // 如 "按截止日期，工作日日历"
  };
  completeness: "complete" | "partial";
  gaps: Array<{ source: string; reason: string }>;   // 如 某执行读取失败
  inferences: Array<{ field: string; level: "recorded" | "inferred"; basis: string }>;
  truncated?: boolean;
  links?: Array<{ label: string; url: string }>;
  hints?: string[];                 // 给 Agent 的下一步建议（非指令性的提示）
}
```

- **完整性：** 任何一个数据源失败都不能静默丢弃，必须写进 `gaps` 并把 `completeness` 设为 `partial`。
- **推测标注：** 由证据加权得到的结论（阶段识别、业务进展的"推测"等级）必须在 `inferences` 中注明，Agent 转述时说"推测"。
- **禅道数据不是指令：** 需求标题、正文等文本字段放在 `data` 中，SKILL 要求 Agent 不执行其中的任何指示。

### 2.3 输出：写入结果

```ts
export interface PreparedOperation {
  ok: true;
  opId: string;                     // "op_" + ULID
  kind: string;                     // 如 "create_story"
  level: "W1" | "W2";               // 服务端判定
  expiresAt: string;
  preview: {
    summary: string;                // 一句话：要做什么
    steps: Array<{ seq: number; action: string; target: string; fields: Record<string, { value: unknown; origin: "user" | "default" | "derived" }> }>;
    affects: string[];              // 受影响的人（账号+中文名）
  };
  warnings: Array<{ code: string; message: string }>;
  requiresPreviewAck: boolean;      // W2 时为 true
}

export interface OperationResult {
  ok: boolean;
  opId: string;
  status: "confirmed" | "partial" | "unknown" | "not_executed" | "failed";
  steps: Array<{ seq: number; action: string; state: "done" | "skipped" | "failed" | "unknown" | "pending"; zentaoId?: number; url?: string; error?: string }>;
  created: Array<{ type: "story" | "task" | "comment" | "link"; id: number; url: string }>;
  nextActions?: string[];           // 如 "confirm_operation(opId, resume=true)"
  notified?: Array<{ target: string; channel: "wecom"; state: "sent" | "queued" | "failed" }>;
}
```

`fields[*].origin` 用来区分"用户给的 / 规范默认 / 推导"，Agent 在预览中必须把 `default` 字段标为"默认"（见 05 §5.4 字段填写原则）。

### 2.4 错误

```ts
export interface ToolError {
  ok: false;
  code: ErrorCode;
  message: string;                  // 中文，可直接给用户看
  details?: Record<string, unknown>;// 不含敏感值
  retryable: boolean;
}
```

| 错误码 | 含义 | 可重试 | Agent 应该怎么做 |
| --- | --- | --- | --- |
| `INVALID_INPUT` | 参数不合法 | 否 | 修正参数 |
| `AMBIGUOUS_ENTITY` | 人、产品、模块、计划名称匹配不唯一 | 否 | 把 `details.candidates` 列给用户选 |
| `NOT_FOUND` | 对象不存在或无权限查看 | 否 | 告知用户 |
| `MISSING_REQUIRED` | 缺少禅道必填字段或规范必填（如本次实现范围） | 否 | 按 `details.missing` 补问 |
| `PREVIEW_REQUIRED` | W2 操作未带 `previewAck=true` | 否 | 先给用户看预览再确认 |
| `PREVIEW_TOO_FAST` | W2 操作生成预览后未满最小确认间隔（同轮自动调用了 confirm） | 否 | 停止调用 confirm，先把预览展示给用户并等待用户回复确认 |
| `PLAN_EXPIRED` | 操作计划过期 | 否 | 重新 prepare |
| `PLAN_STALE` | 执行前刷新发现关键字段已变化 | 否 | 重新 prepare 并说明变化 |
| `CAPABILITY_UNVERIFIED` | 所需写能力未在 #29 验证 | 否 | 告知用户需先验证；给出禅道手工操作链接 |
| `CAPABILITY_DISABLED` | 能力被禁用（完成任务、建 Bug 等） | 否 | 告知用户在禅道操作 |
| `CAPABILITY_CLI_ONLY` | MCP 路径请求仅 CLI 开放的能力 | 否 | 告知用户需使用 CLI |
| `PERMISSION_DENIED` | 禅道拒绝（403）或超出本工具授权 | 否 | 告知用户 |
| `AUTH_FAILED` | 登录失败 | 否 | 提示运行 `bzt doctor` |
| `ZENTAO_UNAVAILABLE` | 网络异常、限流（429）或异常 HTTP 状态（如 5xx） | 是 | 稍后重试 |
| `ZENTAO_TIMEOUT` | 读取超时 | 是 | 稍后重试或缩小范围 |
| `ZENTAO_SCHEMA_MISMATCH` | 响应结构与 DTO 不符 | 否 | 提示管理员（可能禅道升级） |
| `ZENTAO_BUSINESS_ERROR` | 禅道返回业务错误 | 否 | 转述 `message` 和 `error` 中白名单内的诊断短句，截断至 120 字符。无匹配时使用通用提示（06 §2.2） |
| `RULE_VIOLATION` | 违反规范（如激活时缺范围、跨产品未指定配对） | 否 | 按 message 补全；或由有权限的角色豁免 |
| `CONFIG_MISSING` | 缺配置（如模块未配置研发主管） | 否 | 提示配置项 |

服务端仅为 `ZENTAO_UNAVAILABLE` 和 `ZENTAO_TIMEOUT` 派生 `retryable: true`。业务写入已发送且无法确认时按 §2.3 的 `unknown` 处理，进入回读或反查流程。

### 2.5 授权级别判定

见 05 §5.2。服务端规则：

| 条件 | 级别 |
| --- | --- |
| 只读 | W0 |
| 单条、只影响自己（指派给自己、改自己维护的需求元数据） | W1 |
| 影响他人（指派给他人、通知他人）、批量（>1 个对象）、跨产品、移交、拆解、挪月、关闭 | W2 |
| `mode=strict-ai` | 所有写入至少 W2 |

## 3. P1 工具

### 3.1 `resolve_context`

把自然语言里的人、产品、模块、计划、迭代解析成 ID，并给出配置里的角色（设计主管、研发主管、测试负责人）。

```ts
input: {
  people?: string[];                 // "研发主管（后端）" 也可以，按配置解析
  product?: string; module?: string; // "天宫平台/权限管理"
  plan?: string;                     // "12月" / "L3 12月 权限管理"
  execution?: string;
  month?: string;
}
output data: {
  people: Array<{ input: string; account: string; realname: string; team?: string; roles: string[] }>;
  product?: { id: number; name: string; state: "design" | "runtime" | "delivery" | "other" };
  module?: { id: number; path: string; designLead?: string; devLead?: string; testLead?: string };
  plan?: { id: number; title: string; begin: string; end: string; level: "L2" | "L3" };
  execution?: { id: number; name: string; kind: "design" | "dev" | "ui" | "other"; month?: string };
  me: { account: string; realname: string; roles: string[] };
}
```

### 3.2 `get_my_work`

```ts
input: {
  groups?: Array<"new" | "action" | "waiting_ready" | "maintained" | "raised" | "can_start">;  // 默认全部
  horizonDays?: number;              // 临期窗口，默认 3 个工作日
  since?: "last_seen" | string;      // 默认 last_seen
  markSeen?: boolean;                // 默认 true
}
output data: {
  new: Item[];                       // 自上次以来新增到我名下
  action: {                          // 需要我处理
    overdue: TaskItem[]; dueToday: TaskItem[]; dueSoon: TaskItem[]; unscheduled: TaskItem[];
    toReceive: StoryItem[];          // 研发主管：待接收
    toReview: StoryItem[];
  };
  waiting_ready: Array<StoryItem & { waitingFor?: Person }>; // 已指派给我但未就绪，显示在等谁
  maintained: StoryItem[];           // 我是状态维护人，含已移交研发的
  raised: StoryItem[];               // 我提的 / 我是反馈者
  can_start: {                       // 按角色
    tests: TaskItem[];               // QA：上游研发已完成、可以开始的测试
    upcomingTests: TaskItem[];       // QA：研发即将完成
    acceptDeliver: TaskItem[];       // DS：测试完成后的验收、交付
  };
  parentRisks?: ParentRisk[];
}
```

- 逾期与临期只计叶子任务（Q5），口径见 04 §4.2。
- `waiting_ready` 中的需求不计入 `action`（US-RM-09）。
- 状态维护、未就绪、接收与评审分组聚焦未关闭需求。
- `maintained` 先按提出人、当前处理人、模块设计主管与本地 `story_roles` 缓存筛选；存在未读取正文标签的未关闭需求时，在 `inferences` 和 `hints` 明示仅标签指定的维护人可能漏列，并提示通过 `query_stories(role="maintainer")` 刷新本地角色缓存。
- 返回 `new` 且新增判定所需数据源完整时，`markSeen=true` 推进 `seen_cursor`。详情或 Bug 等辅助源失败时保留缺口。

### 3.3 `get_team_work`

```ts
input: {
  team?: string;                     // 默认：我作为主管的团队
  members?: string[];
  view?: "overdue" | "due_soon" | "all_open";   // 默认 overdue
  groupBy?: "member" | "story" | "execution";   // 默认 member
  product?: string;
}
output data: {
  groups: Array<{ key: string; label: string; count: number; items: TaskItem[] }>;
  totals: { overdue: number; dueSoon: number; open: number };
  parentRisks?: ParentRisk[];
}
interface ParentRisk { task: TaskItem; allChildrenFinished: boolean | null; reason: string }
```

- `due_soon` 只含今日之后、临期窗口内到期的叶子任务。今日到期为 `due_today`，可在 `all_open` 中查看。
- 父级风险单列，不计入任务总数。数据不完整时，总数仅覆盖已确认归属的已读任务。

### 3.4 `get_member_schedule`

```ts
input: {

  bucket?: "day" | "week";           // 默认 week
```

### 3.7 `create_story`

```ts
input: {
  product: string; module: string;
  title: string;
  category?: "feature" | "design";   // 不填时按 03 N02 判定表推荐，返回到 preview 让用户确认
  spec: { background: string; scope: string; designRef?: { doc: string; section: string; version?: string }; notInScope?: string };
  verify: string;
  plan?: string;                     // L3；默认：模块的本月 L3
  version?: string;                  // 写入关键词 "版本:Vx.y.z"
  pri?: 1 | 2 | 3 | 4;               // 默认 3
  source?: string; sourceNote?: string;
  feedbackBy?: string;               // 中文名，自由文本保留
  maintainer?: string;               // 状态维护人，默认：我（若我是设计人员）或模块设计主管
  assignTo?: string;                 // 草稿阶段默认指派状态维护人（N05）
  requirementId?: number;            // 回关联用户需求（US-DM-02）
  pair?: { product: string; module: string; title?: string };   // 跨产品一次建两条（US-DM-04）
  derivesFrom?: number;              // 由设计类需求派生
  crossModule?: boolean;             // true 时接收人 = 被依赖模块研发主管（US-DS-04）
  backfilled?: { actualStartedAt: string };   // 先做后录（N15）
  states?: { activate?: boolean };   // 默认 false：草稿
  intake?: { rawText: string; channel: "wecom" | "verbal" | "meeting" | "zentao" | "other" };
}
output: PreparedOperation & { intakes: Array<{ intakeId: string; message: string }> }
```

- 预检：禅道必填 + 规范必填（本次实现范围 `spec.scope`；引用设计文档时必须有章节）。缺失返回 `MISSING_REQUIRED`。
- 正文按 03 N03 模板生成，末尾写角色标签 `<!-- bzt:v1 maintainer=...;receiver=...;intake=... -->`。
- `pair` 生成两条 `story.create` + 一条 `story.linkStory`；`requirementId` 追加 `requirement.linkStory`。
- `crossModule=true` 时表示跨模块提依赖需求：接收人默认解析为目标被依赖模块的研发主管，状态维护人为当前发起方设计人员；若已知上游需求，应同时传入 `derivesFrom` 建立"衍生自"关系（US-DS-04）。
- `states.activate=true` 等价于创建后立即走 `handoff_story(mode=activate)`，级别升为 W2。
- 单条、指派给自己时为 W1；其余 W2。

示例（W1，同一轮可执行）：

```json
// → create_story
{"product":"天宫平台","module":"权限管理","title":"角色列表支持按部门筛选",
 "spec":{"background":"运营反馈角色多时难找","scope":"角色列表页增加部门筛选；不含导出"},
```

### 3.11 `confirm_operation`

```ts
input: { opId: string; previewAck?: boolean; resume?: boolean; excludeSteps?: number[] }
```

- W2 且 `previewAck !== true` → `PREVIEW_REQUIRED`。

## 4. P2 工具

### 4.1 `get_plan_progress`

```ts
input: {
  view: "plan" | "release" | "commitment" | "iteration";
  product?: string; plan?: string; month?: string; version?: string; execution?: string;
  groupBy?: "owner" | "module" | "progress";
}
```

| view | 回答的问题 | 主要输出 |
| --- | --- | --- |
| `plan` | "8 月计划下的研发是否完成"（US-PM-01） | L3 汇总：已完成 / 执行中 / 待接收 / 未就绪 / 已取消 / 无法判断，按负责人分组；去重后叶子需求计数 |
| `release` | 版本是否可以发布（US-PM-02、US-QA-03） | 门禁：测试完成率、1–2 级未关闭 Bug、例外登记；距发布日 |
| `commitment` | 月初承诺兑现（US-PJ-02） | 快照 vs 当前：兑现、顺延（含原因）、新增插入 |
| `iteration` | 迭代指标（US-PJ-03） | 拆解及时性、逾期率、测试周期中位数 |

### 4.2 `get_monthly_dev_queue`

```ts
input: { team?: string; month?: string; includeNotReady?: boolean }
output data: {
  buckets: { toReceive: StoryItem[]; inDev: StoryItem[]; carriedOver: StoryItem[]; planNoIteration: StoryItem[]; iterationNoPlan: StoryItem[] };
  notReady?: StoryItem[];
  monthEndWarnings?: StoryItem[];    // 月最后 7 个工作日：阶段任务未开始
}
```

五桶定义见 04 §4.6 月度范围。

### 4.3 `decompose_stories`

```ts
input: {
  storyIds?: number[]; taskId?: number;      // taskId 用于 template=subtasks
  template: "design" | "feature" | "next_stage" | "subtasks";
  execution?: string;                        // 默认：按 03 N04 命名找本月对应职能迭代
  assignees?: Partial<Record<"design"|"review"|"handoff"|"dev"|"interface"|"test"|"acceptance"|"delivery", string>>;
  dates?: Partial<Record<string, { estStarted?: string; deadline?: string }>>;
  estimates?: Partial<Record<string, number>>;
  include?: { interface?: boolean; delivery?: boolean };   // 按需阶段
  subtasks?: Array<{ name: string; assignTo: string; deadline?: string; estimate?: number }>;
  notify?: boolean;                          // 默认 true（US-RM-11）
}
output: PreparedOperation
```

| template | 生成 | 规范 |
| --- | --- | --- |
| `design` | 【设计】【评审】【传递】 | N06 |
| `feature` | 【研发】（【接口】按需）【测试】【验收】（【交付】按需），一次建齐 | N07（研发类） |
| `next_stage` | 只补缺失的阶段任务 | 修复 R02、R11 |
| `subtasks` | 在指定任务下建子任务 | N08 |

- 前置步骤自动加入：需求未关联执行时先 `story.linkExecution`；需求未激活时拒绝并建议 `handoff_story`。
- 默认日期规则见 03 N07；用户未给出的日期 `origin=default`。
- 拆解视为"接收"（N09），执行后从"待接收"中移除。

### 4.4 `handoff_story`

```ts
input: {
  storyId: number;
  mode: "from_design" | "activate";
  // from_design：从已评审的设计类需求生成研发类需求
  feature?: { product?: string; module?: string; title?: string; scope?: string; designRef?: { doc: string; section: string; version?: string } };
  receiver?: string;                 // 默认：模块（或被依赖模块）研发主管
  comment?: string;
  notify?: boolean;                  // 默认 true
}
output: PreparedOperation
```

| mode | 步骤 |
| --- | --- |
| `from_design` | 校验设计类需求的【评审】已完成 → `story.create`（feature，派生关系，正文继承范围与设计章节）→ `story.linkStory` → `story.activate` → `story.assign`（研发主管）→ `story.comment`（移交说明）→ 在返回结果的 `nextActions` 中强高亮输出原设计需求【传递】任务与需求本身的直达链接，提醒用户顺手完成并关闭设计需求（事实性状态不代填） |
| `activate` | 校验本次实现范围存在（否则 `RULE_VIOLATION`）→ `story.activate` → `story.assign`（研发主管）→ 更新角色标签 `receiver` → `story.comment` |

### 4.5 `reschedule_story`

```ts
input: { storyIds: number[]; toMonth: string; reason: string; moveTasks?: boolean }
output: PreparedOperation
```

步骤：改计划到目标月 L3 → 可选调整未完成任务所属迭代与日期 → `story.comment` 写入挪月原因 → 本地 `reschedules` 记录。`reason` 必填。

### 4.6 `close_stories`

```ts
input: {
  mode: "story" | "cleanup";
  storyIds?: number[];               // mode=story
  closedReason?: "done" | "cancel" | "duplicate" | "postponed" | "willnotdo";
  cleanup?: { scope: { team?: string; execution?: string; beforeMonth?: string }; classes?: Array<"A" | "B" | "C"> };  // R14 分类
}
output: PreparedOperation
```

- `story`：关闭需求 + 一并关闭其已完成任务（N14）；有未完成任务时警告并要求用户决定（关闭或保留）。
- `cleanup`：按 R14 A/B/C 列出待清理任务，C 类（无关联需求）只列出不关闭。只关不删。

### 4.7 `set_story_meta`

```ts
input: {
  storyId: number;
  stageRequirements?: Partial<Record<"interface" | "delivery" | "acceptance" | "test", { required: boolean; reason?: string }>>;
  waiver?: { rule: string; reason: string };       // 规则豁免、发布门禁例外（由产品管理登记）
  roles?: { maintainer?: string; receiver?: string };
  scope?: { scope: string; designRef?: { doc: string; section: string; version?: string } };
  version?: string;
}
output: PreparedOperation
```

- 改正文角色标签、范围、关键词需要 `story.edit`；阶段要求和豁免写本地表并同步一条 `story.comment` 留痕。
- 发布门禁例外只允许配置中的产品管理角色登记，否则 `PERMISSION_DENIED`。

## 6. 工具描述写法（给 Agent 看的 description）

单人门户通过 `bzt web [--config 路径] [--port 端口]` 启动。登录后按团队角色映射开放现有契约的子集，角色和对应页面见 [CR-002](changes/CR-002-local-web-portal.md)。页面读取保留范围、缺口和推测，写入仅能确认当前会话、当前职责已经预览的操作编号。W2 的最小确认间隔与 CLI、MCP 共用同一执行器。

本机启动器可复用已配置的凭据。身份验证后，仅本机使用者的会话返回本人可维护的职责清单及版本。保存职责需要同源请求、当前账号和读取时的版本，服务端返回更新后的身份与可用页面。初始化用例见 [CR-003](changes/CR-003-portal-onboarding.md)。

门户按业务场景组合上述工具。测试人员可用 `get_plan_progress` 的 `release` 视图查询门禁，例外登记仅开放给有对应写入权限的职责。本机使用者拥有提需职责时，身份接口同时提供当前配置中的可选产品与模块。页面映射见 [CR-004](changes/CR-004-prototype-alignment.md)。

伏羲第 11 版中的内部职责可读取本月队列和版本门禁。月度计划、承诺和迭代视图限产品管理、项目管理。研发和测试人员打开排期时，门户把成员范围固定为本人并拒绝临时指派试算。研发人员查本人完整任务时可用 `get_team_work` 的 `all_open` 视图，服务端固定本人。设计、研发人员和测试人员的风险巡检限本人。设计主管的批量导入通过 `import_stories` 预览与确认执行。

每个工具的 MCP `description` 统一结构，控制在 400 字以内：

```text
用途：一句话。
何时用：用户说……时。
不要用于：……（指向正确工具）。
注意：W2 先展示预览；输出含 scope/completeness，需要转述口径。
```

示例（`get_my_work`）：

```text
用途：查看当前账号需要关注的工作，按"新增 / 需要我处理 / 已指派但未就绪 / 我维护的 / 我提的 / 可开始"分组。
何时用：用户问"我今天有什么要做""有没有新任务""我的逾期"。
不要用于：查团队成员（用 get_team_work）、查某条需求细节（用 get_story_progress）。
注意：逾期只算叶子任务；转述时说明数据时间。
```
