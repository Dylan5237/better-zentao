# 13 术语与追溯

## 1. 术语表

### 1.1 角色

| 术语 | 代号 | 定义 |
| --- | --- | --- |
| 业务反馈者 | FB | 提出原始诉求的业务方（运营、交付、客户代表等），通常不直接使用禅道 |
| 产品管理 | PM | 负责产品路线、L2/L3 计划、版本发布与发布门禁例外 |
| 项目管理 | PJ | 负责节奏、巡检、月度快照与规范执行度量 |
| 设计主管 | DM | 负责模块设计质量与需求维护，如设计主管（前端）；关闭需求的最终责任人（A） |
| 设计人员 | DS | 写需求、做设计、维护需求状态（通常就是状态维护人），负责验收与交付 |
| 研发主管 | RM | 接收需求、拆解任务、分配人员、周期清理，如研发主管（前端）、研发主管（后端） |
| 研发人员 | RD | 执行研发、接口任务，可拆子任务 |
| 测试人员 | QA | 执行测试任务、提交 Bug；测试负责人负责测试排期 |

### 1.2 需求人员字段

| 术语 | 定义 | 存放位置 |
| --- | --- | --- |
| 反馈者 | 原始诉求的提出方 | 禅道 `feedbackBy`（自由文本） |
| 提出人 | 在禅道建这条需求的人 | 禅道 `openedBy` |
| 状态维护人 | 负责完善需求、推进状态、最终收尾的人 | 正文角色标签 `maintainer` |
| 当前处理人 | 下一步要行动的人 | 禅道 `assignedTo`（N05） |
| 接收人 | 负责接收并拆解的研发主管 | 正文角色标签 `receiver` |

### 1.3 对象与结构

| 术语 | 定义 |
| --- | --- |
| 业务需求 / 用户需求 / 研发需求 | 禅道三级需求：`epic` / `requirement` / `story`。本文"需求"默认指研发需求 |
| 设计类需求 / 研发类需求 | 研发需求的 `category`：`design` / `feature` |
| 配对需求 | 同一原始诉求在设计态、运行态两个产品分别建的研发需求，互相关联 |
| 派生需求 | 设计类需求评审通过后，由移交生成的研发类需求 |
| 原始诉求（intake） | 用户口头、企微或会议中提出的原话，本地记录并与需求关联 |
| L2 计划 | 产品计划顶层，表达建设目标 |
| L3 计划 | L2 的子计划，规范为"月 × 模块（负责人）"（N04） |
| 版本标签 | 需求关键词中的 `版本:Vx.y.z` |
| 发布日历 | 版本 → 发布日期的对照，由产品管理维护 |
| 迭代（执行） | 禅道执行，按"产品 × 职能 × 月"建立 |
| 阶段任务 | 带阶段前缀的任务：【设计】【评审】【传递】【研发】【接口】【测试】【验收】【交付】 |
| 阶段标记 | 本系统建任务时写在描述中的 `<!-- bzt:stage=... -->` |
| 角色标签 | 本系统写在需求正文末尾的 `<!-- bzt:v1 maintainer=...;receiver=...;intake=... -->` |
| 叶子任务 | 没有子任务的任务；所有统计只计叶子 |
| 多人任务 | 禅道 `linear` / `multi` 模式任务；新建不再使用（N08） |

### 1.4 状态与口径

| 术语 | 定义 |
| --- | --- |
| 记录状态 | 禅道原生状态（draft / reviewing / active / changing / closed 等） |
| 业务进展 | 系统按阶段任务推导的进展（未就绪、待接收、研发中、待测试、测试中、待验收、待交付、可关闭、已完成等，见 04 §4.4–4.5） |
| 未就绪 | 需求仍为草稿或评审中，研发不能开始 |
| 待接收 | 已激活并移交研发主管，但尚未拆解 |
| 接收 | 研发主管完成拆解即视为接收（N09） |
| 缺口 | 应有的下游阶段任务不存在 |
| 滞留 | 超过阈值未推进 |
| 逾期 | 叶子任务未完成且截止日期早于今天 |
| 临期 | 截止日期在未来 N 个工作日内（默认 3） |
| 五桶 | 本月研发队列：待接收、在研、上月遗留、计划有但未排迭代、迭代有但缺计划 |
| 承诺快照 | 月初保存的本月计划需求清单，用于月底对比兑现与顺延 |
| 发布门禁 | 版本内需求测试完成且 1–2 级 Bug 清零（N12） |
| 禅道可见投入 | 禅道中记录的工时与任务，不等于实际工作量（N16） |
| 记录 / 推测 | 结论的证据等级：来自禅道明确记录 / 由多项证据加权推导 |
| 完整性 | 查询是否所有数据源都读取成功：complete / partial |

### 1.5 系统

| 术语 | 定义 |
| --- | --- |
| better-zentao | 本系统；命令行为 `bzt` |
| MCP | Model Context Protocol，Agent 调用工具的协议；本系统使用本地 stdio 方式 |
| Skill | 给 Agent 的使用说明（`SKILL.md`），包含路由、补问与表达规范 |
| 两段式 | 写入先 prepare 生成预览与 `opId`，再 confirm 执行 |
| W0–W3 | 写入授权级别（05 §5.2） |
| 五态 | 写入结果：confirmed / partial / unknown / not_executed / failed |
| 能力注册表 | 记录每个禅道写能力是否已验证 |
| #29 | 禅道研发验证项目，唯一允许试验写入的产品 |
| DTO 白名单 | 只保留声明字段的数据投影，防止敏感字段外泄 |

## 3. 反向检查

| 检查 | 结论 |
| --- | --- |
| 每个痛点至少对应 1 条用户故事 | 是（P01–P27） |
| 每条 P1 用户故事至少对应 1 个工具与 1 个验收场景 | 是，见 07 §1 与 09 §5 |
| 每个工具至少服务 1 条用户故事 | 是，见 07 §1 |
| 每条规则（R01–R16）有处理人与建议 | 是，见 04 §5 与 07 `RiskHit.suggestion` |
| 没有对应痛点、却新增的能力 | 设计类进展视图（US-DM-06）、承诺快照（US-PJ-02）：来自管理目标"看计划质量"（S1），保留 |
