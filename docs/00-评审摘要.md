# 00 评审摘要：better-zentao（禅道 + 本地 Agent 协作方案）v3.0

> 一页纸给评审会与领导。细节见 README 中的文档地图。需要拍板的事项在最后一节。

## 1. 要解决什么问题

天宫团队（设计态"天宫平台"、运行态"OneLink 7.0"）在禅道 22.6 上协作，访谈整理出 27 个痛点，集中在四件事：

1. **提需求难**：业务反馈者不愿用禅道，设计主管大量代录；研发先做后录。
2. **流转靠人记**：草稿就指派给研发，研发不知道该做什么；研发完成后测试迟迟不建；不另外告知研发就感知不到新需求。
3. **看不清**：本月要研发哪些需求、L3 计划完成了没有、版本能否发布、每个人手上排了什么，都要在多个页面间拼凑。
4. **记录不统一**：计划有按"月 × 负责人"的也有按版本的；任务有多人任务也有子任务；范围不写清；Bug 不关联需求。

## 2. 根因

| 根因 | 说明 |
| --- | --- |
| C1 入口门槛高 | 提需要懂产品、模块、计划、类别、必填项 |
| C2 `指派给`含义混乱 | 同一字段既表示"下一步谁行动"又表示"最终谁接收" |
| C3 接续靠记忆 | 下游任务等上一阶段完成后才有人想起来建，没有通知 |
| C4 计划语义不统一 | 一条需求只能挂一个计划，"月度目标"与"版本"互相挤占 |
| C5 信息分散 | 需求、计划、迭代、任务、Bug 分布在不同视图 |
| C6 记录不规范 | 范围、关联、收尾缺失，禅道外的工作没有记录 |

**判断：** 只做工具解决不了 C2、C3、C4、C6，它们是**做法问题**。因此方案分两部分：**一套统一的协作规范 + 一个按规范提供默认值和提醒的 Agent 工具**。团队之间的不同做法不做成配置开关，而是评审后统一成一种（ADR-10）。

## 3. 推荐的统一规范（17 条，核心 6 条）

| 编号 | 规范 | 一句话 | 对谁有帮助 |
| --- | --- | --- | --- |
| N04 | L3 = 月 × 模块（负责人）；版本用标签 + 发布日历 | 计划只表达月度目标，版本另行标注 | 产品管理能统一按 L3 看完成情况；研发主管（后端）仍有版本视图，还多了测试与 Bug 信息 |
| N05 | 指派即行动 | 草稿指派状态维护人，激活后指派研发主管，测试完成转回状态维护人 | 研发只看到能做的；设计随时找得到自己维护的需求 |
| N07 | 拆解时一次建齐阶段任务 | 【研发】【接口】【测试】【验收】【交付】，日期默认填写 | 测试能提前排期；"研发完成测试未建"从结构上消除 |
| N03 | 研发类需求必须写"本次实现范围" | 引用设计文档要写章节与版本 | 研发不用再分辨旧设计 |
| N12 | 发布门禁 | 测试完成 + 1–2 级 Bug 清零；例外由产品管理登记 | 发布质量可控、可追溯 |
| N17 | 通知走摘要 | 企微群机器人每日摘要 + 关键事件推送，同一事项一天一次 | 不再依赖口头通知，也不增加打扰 |

其余：来源必登记（N01）、先判断是否需要设计（N02）、设计三段任务（N06）、协作用子任务（N08）、接收时限 3 个工作日（N09）、跨模块提给研发主管（N10）、Bug 必关联需求（N11）、挪月留痕（N13）、关闭即收尾（N14）、先录后做（N15）、工作量只作参考（N16）。

## 4. 系统方案

- **形态：** 每人本机安装 `bzt`，作为本地 MCP 服务接入 Codex / Claude Code / Gemini，用自己的禅道账号，另有命令行与定时任务（摘要推送、月度快照）；并同步提供 **Web 门户协作工作台**（与本地 MCP / CLI 共享同一业务内核、领域口径与两段式安全写入模型，禅道仍为唯一事实来源，不做独立工作流引擎）。
- **能力：** 19 个按意图设计的工具，例如"我今天要做什么""帮我提个需求""这个需求到哪了""前端组未来 4 周排期""8 月计划完成了没有""批量拆解这 5 条需求""把这条移交研发"。
- **安全：** 写入一律先预览、再确认；影响他人或批量的操作必须向用户展示预览；删除、完成任务、填写工时不开放给 Agent；事实性字段不代填；接口返回的敏感字段（如密码哈希）在适配层丢弃；所有写能力先在验证产品 #29 上实测。
- **准确：** 统计只计叶子任务；数据读取不完整时明确说明"不完整"；推测的结论标注"推测"。
