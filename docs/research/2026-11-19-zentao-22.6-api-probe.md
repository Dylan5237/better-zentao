## 三、实测发现的 8 个关键 22.6 行为差异与坑点

1. **v2 响应安全与体积红线（极重要）**
   - 实测 `GET /api.php/v2/my/todo` 返回的 `user` 对象中包含 32 位 `password` 哈希字段；且多个 v2 列表端点每次请求都会夹带全公司 2,086 人的 `users` 字典（单次 70KB~140KB）。
   - **约束**：必须在 API 适配层做**严格 DTO 白名单投影**，绝不允许将 v2 原始响应透传给上层、MCP 输出或日志。
2. **用户目录分页与字段差异**
   - `v1/users` 仅返回 `{ account, realname }`，缺少 `id / dept / role / pinyin`；`v1/users/{id}` 非管理员会返回错误。
   - 需结合 `v1/departments`（44ms）与 `v2/users?recPerPage=3000&pageID=1`（388ms）建立带 TTL 的本地目录缓存。
3. **需求列表端点（`v1/products/{id}/stories`）特殊行为**
   - 正常响应 HTTP 状态码为 **`201`**（不可硬编码校验 `=== 200`）；
   - 不传 `status` 默认等同 `status=unclosed`；传 `status=all` 返回全量（含 `closed`）；传具体枚举 `active / draft / closed / changing / reviewing` **全部返回 `total=0`**，具体状态过滤必须在客户端侧执行；
   - 传 `type=requirement` 时会无视 `limit` 并把 `requirement` 与 `story` 混合返回，查用户需求应使用 `v2/product/browse?storyType=requirement` 或显式按 `item.type` 过滤。
4. **需求详情内嵌任务缺少截止日期与工时**
   - `GET /api.php/v1/stories/{id}` 的 `tasks` 数组仅含 `{ id, name, type, status, assignedTo }`，不含 `deadline / left / consumed`。聚合需求进度与逾期状态时，需结合 `story.executions` 或任务详情补齐。
5. **父子任务扁平返回，逾期统计须防双算**
   - `v1/executions/{id}/tasks` 同时扁平返回父任务（`isParent: 1`）与子任务（`parent > 0`），且父任务自身也会带 `deadline`。统计逾期数与负载时必须区分叶子任务与父任务汇总行。
6. **多人协作任务（`mode: "linear" | "multi"`）**
   - 现网存在 `linear` 与 `multi` 多人任务。列表 `assignedTo` 仅显示当前顺位人，完整协作成员在详情 `team` 数组中；且 `team[].realname` 为禅道缺陷（返回了记录 ID 字符串），须以 `account` 反查用户目录映射中文名。
7. **任务未完成状态枚举比常规更多**
   - 现网实测状态包含：`wait`、`doing`、`pause`、`changed`（需求变更待确认）、`done`、`closed`、`cancel`。未完成判定应采用 `not in (done, closed, cancel)`，并与服务端 `status=delayed` 一致。
8. **现网动态必填规则（`/api.php/v1/requiredFields` 实测）**
   - `story.create`: `["title", "module", "assignedTo", "verify", "spec"]`（沿用旧项目实测验证的 22.6 创建红线：显式传 `reviewer: []`、`status: "draft"`，必填含 `assignedTo` 时走 `POST /api.php/v2/stories?productID=...` 并双写 `module` 与 `modules: [module]`，创建后 GET 回读确认，禁止未确认时重试创建）。
   - `task.create`: `["execution", "name", "type", "module", "assignedTo", "estStarted", "deadline", "desc", "pri"]`。
   - `task.finish`: `["realStarted", "finishedDate", "currentConsumed"]`。
   - `bug.create`: `["title", "openedBuild", "module", "assignedTo", "type", "severity", "steps", "pri"]`。

## 四、业务域命名与实况特征（天宫设计态 + OneLink 7.0 运行态）

- **双态产品与项目对应**：
  - 设计态：`天宫平台（正式）`（Product `#42` / Project `#179`）；
  - 运行态：`OneLink 7.0（正式）`（Product `#43` / Project `#180`）；
  - 其他相关产品：`运营交付平台（正式）(#44)`、`【研发】天宫平台(#15)`、`天宫需求反馈池(#3)`、`禅道研发验证项目(#29)`（专用受控冒烟产品）。
- **计划层级（L2 → L3）**：
  - `#42` 顶层计划为 `【L2-建设目标】...`（`parent: -1`），子计划嵌套在 `children` 数组中，命名常见 `【负责人】...`；
  - **关键实测**：部分 L3 计划标题不含月份字样，但均有规范的 `begin` / `end` 日期（如 `2026-11-01` ~ `2026-11-30`），因此按月过滤 L3 计划必须以**起止日期重叠为主、标题月份为辅**。
- **用户需求（Requirement）API 差异**：
  - 实测 `GET /api.php/v1/stories/{reqId}` 对 `type="requirement"` 的 ID 返回 HTTP **400**，不可与 `story` 混用 v1 详情端点，需走 v2 或专用 requirement 接口。
- **设计类 vs 研发类需求**：
  - `#42` 与 `#43` 均启用了 **`category: "design"`**（设计类研发需求）与 **`category: "feature"`**（功能/研发类研发需求），旧项目 `STORY_CATEGORIES` 枚举缺失 `"design"`，新项目须纳入。
- **迭代分工**：
  - 同一产品项目下按月且按职能拆分迭代（如 `【天宫平台】【设计】11月迭代`、`【天宫平台】【研发】11月迭代`、`11月UI设计迭代计划`）。
- **任务与流程特征（#179 / #180 实测抽样 675 条任务）**：
  - 实测活跃任务 `type` 覆盖 `devel(443) / design(164) / test(53) / ui(6) / study(5) / misc(3) / discuss(1)`；命名常见职能前缀（如 `【前端研发】/【后端开发】/【前端测试】`）；
  - **关键实测**：部分“功能验收”“原型设计”“原型设计评审”任务在现网仍沿用了禅道默认 `type="devel"`，因此环节识别与风险扫描**不可仅看 `task.type`**，须结合 `story.category` + 迭代类型 + `task.type` + 标题关键词 + 负责人角色复合判定；
  - 实测存在**研发任务已全完成但未创建测试任务**的活跃需求风险场景；
  - 实测存在 `feedbackBy` 自由文本字段（可能为单个或顿号分隔多个中文姓名）。

## 五、性能基线（设计缓存与并发策略依据）

- 组织目录初始化（424 部门 + 2,086 全量用户）：**~430ms**（缓存 10~30 分钟）。
- 我的地盘 / 我的贡献单次查询：**50~110ms**。
- 全公司 116 个未关闭执行（2,634 条任务）并发=8 全量扫描：**1.78 秒**；结合 `status=delayed` / `status=undone` 及短时缓存，团队逾期看板可稳定控制在 **1 秒内**。
